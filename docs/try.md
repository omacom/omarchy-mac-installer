# Try Omarchy in a VM

The installer is the one app for Omarchy on a Mac, with two modes. **Install** puts Omarchy on the Mac's own hardware. **Try** runs it in a virtual machine, in a window beside macOS. The design record is Try Omarchy's [one app plan](https://github.com/omacom/try-omarchy/blob/main/docs/one-app.md); how the VM runs is in its [VM kit and run mode](https://github.com/omacom/try-omarchy/blob/main/docs/vm-kit.md).

## What people see

- The first page is the landing page: this Mac in a line, a few short lines, then two buttons of the same width side by side at the bottom, **Install on this Mac** on the left and **Try it in a VM** on the right. The lines say why Install is unavailable, what Try has and the space for it. With nothing to say, one line names both choices. The page keeps its height in every state, and the window opens centred on the screen at every launch.
- **Install on this Mac** continues into the plan. While the installer checks the Mac, the button is unavailable, and the lines say so with a spinner.
- When Omarchy can't be installed, Install stays unavailable, and the lines give the reason: the Mac model, too little space, or what else holds this Mac back. **Details** shows the whole reason, with the supported models when the Mac model is the reason, and **Check again** checks the Mac again.
- On a Mac with Omarchy installed, Install is unavailable, and the line says Omarchy is installed. **Remove Omarchy…** stays in the Installation menu. An install still waiting for its Recovery step shows the Recovery steps instead. If Omarchy started before the check found it, the running page says so, and the steps appear once Omarchy shuts down.
- **Try it in a VM** is always available. It opens the Try page, whose **Back** returns to the landing page. The Try page offers Accessibility, so ⌘ works as Super, and the microphone and camera. All three are optional. It shows the space the virtual machine needs and the space free on the disk that holds or will hold it, and **Download and launch** waits until there is room.
- Once a virtual machine exists, the lines say Omarchy is set up and ready, and the space free on its disk, and the left button reads **Migrate to Native**. Without one, they name the space only when a new one wouldn't fit. It is available when Install would be, and unavailable for the same reasons. It opens a sheet that offers to bring the virtual machine's files along ([migrating to native](#migrating-to-native)). **Install Without Migrating** continues as Install on this Mac does, and the virtual machine stays.
- The free space in the header and on the Try page is one reading, rounded the same way, so the same disk shows the same number on both.
- **Allow** for Accessibility first resets this app's own Accessibility decision, as Try Omarchy's launcher does, so a row left by an earlier build can't hold the switch. It then asks macOS from this app, so macOS shows its prompt and lists Omarchy Installer in Privacy & Security › Accessibility, which then opens. Only the person turns it on there. Allow for the microphone or the camera shows macOS's prompt, or opens its pane once refused. The page reads the permissions again when the app becomes active and when System Settings quits.
- While Omarchy runs, the installer's window closes once Omarchy's window is up, and the app leaves the Dock, as Try Omarchy's launcher does, so Omarchy's window is the one Dock tile. Quit in Omarchy's own menu shuts it down. The window, the Dock tile and the menus come back when Omarchy shuts down or fails, with the Try page and **Launch**, or the failure. Opening the app again from the Finder brings the window back while Omarchy runs.
- The running page, shown when the app is opened again while Omarchy runs, has Omarchy's state, **Shut Down** and, on a Mac that can install, **Migrate to Native**, which shuts Omarchy down first. It lists any permission still not granted, with **Allow**; a grant takes effect at the next start.
- A virtual machine in Try Omarchy's default folder is the remembered choice. With one, the app opens on the Try page, with **Allow** and **Launch**, and checks the Mac in the background. Nothing starts until the person presses Launch, and **Back** leads to the landing page. Without one the landing page shows. After Omarchy shuts down, the Try page stays, with **Launch** and **Back**.
- The Installation menu has **Install on this Mac…**, or **Migrate to Native…** once a virtual machine exists, which do what the button does, or say why this Mac can't install. **Delete Virtual Machine…** asks first, naming the most space it frees, with Cancel as the default button. It then moves the folder to the Trash and returns to the landing page.
- Quitting shuts Omarchy down first, bringing the window back with **Shutting down** until it has. The person can't close the window while Omarchy runs.
- When Try Omarchy, or another copy of this app, has the virtual machine open, starting fails and says so, with **Try Again** and **Back**. Try Again is offered on every failure that starting again can help.
- When the virtual machine's settings choose bridged networking but its daemon isn't set up, Omarchy starts with shared networking, and the running page says so with **Set Up Bridged Networking**. That registers the daemon in this app's name, and **Open Login Items** follows while macOS waits for approval. The next start uses it. When the daemon is set up but doesn't answer, the button is **Repair**. **Repair Bridged Networking** and **Remove Bridged Networking** in the Installation menu ask first, with Cancel as the default button, and shut Omarchy down first. When one fails, an alert says why. While a kit fetched after this app was built runs, the line says its bridged networking isn't available yet, with no button, and Repair is unavailable.
- The plan review notes the space the virtual machine takes, as an upper bound, because its disk shares blocks with the image it was cloned from. The native install leaves it in place.

## Coming from Try Omarchy

People who used Try Omarchy 1.2 keep what they had in its default folder. The installer runs the same kit, and always on the default folder, `Application Support/Try Omarchy/VM/v1`.

- **Carries over:** the virtual machine, with everything saved in it, and its settings. The first launch opens on the Try page with **Launch**, and **Back** leads to the landing page with **Migrate to Native** and **Try it in a VM**.
- **Stays Try Omarchy's:** a virtual machine moved to another folder or disk in Try Omarchy. The installer doesn't use it, and offers a fresh download into the default folder instead.
- **Doesn't carry over:** permissions. macOS grants them to each app, so the Try page shows **Allow** for Accessibility, the microphone and the camera again.
- **Bridged networking** needs **Set Up Bridged Networking** once in this app, because its daemon is registered in the name of the app that set it up. Until then Omarchy starts with shared networking. A kit fetched after this app was built can't use bridged networking yet ([known limit](#newer-kits)).

## Migrating to native

Omarchy exports the home folder from inside the virtual machine with **Setup → Move to Native Install**, encrypted with a transfer passphrase. Only virtual machines the installer runs offer it, and only when this installer can stage the export (`TrialRunConfiguration.offersNativeExports`): the configuration asks the kit's run mode for the outbox with `nativeExports`, and Try Omarchy on its own doesn't. The kit client drops the request for a kit whose manifest doesn't list `native-exports`. The launcher publishes the export to Try Omarchy's Exports folder when the virtual machine stops. The contract is Try's [native install export](https://github.com/omacom/try-omarchy/blob/main/docs/native-install-export.md).

**Migrate to Native** opens a sheet that depends on what it finds:

- **An export in Exports:** it names the newest one and checks it against its receipt, without the passphrase. **Install with These Files**, the default button once the check passes, shuts Omarchy down if it runs and continues into the plan with that export chosen. The plan review names it.
- **A finished export in the running virtual machine's outbox:** **Shut Down Omarchy** shuts it down, the launcher publishes the export, and the sheet then offers it as above. Only the outbox's folder names are read; exports come from Exports alone.
- **No export:** the sheet says how to make one, with **Cancel** as the default button.

**Install Without Migrating** is in every case, and drops any chosen export. With an export chosen, the plan needs room to stage it, claim it and import it (`TryExportStagingRegion.additionalInstallBytes`), and the smallest Omarchy the plan offers grows to match. When even the largest doesn't fit, the plan review says so and the install goes ahead without it. After the install, the helper stages the export onto the new Root partition, and the Recovery page says whether it did ([native import](native-import.md)). The sheet's words live in `PlainLanguage+Trial`, its cases in `TrialMigrationOffer`, and `TrialSession.chooseInstall` opens it.

## How it is built

- `TrialSession` is Try's state machine beside the installer's `InstallerSession`. It follows the installer's inspection through `TrialInstallStatus`, which decides what the landing page's Install button offers. `TrialSession.landing` holds both buttons, the lines above them and Install's state, and `installReason` says why Install is unavailable, for the page and the menu.
- `VolumeFreeSpace` reads the space free on a volume, as macOS makes it available for important use. The header reads it for macOS's disk and the Try page for the virtual machine's, and both round with `PlainLanguage.bytes`.
- `LiveTrialEnvironment` runs the embedded kit, or a newer one it fetched ([newer kits](#newer-kits)), through `VMRunClient`, reads and requests this app's permissions, and uses Try Omarchy's default folder, the client's `TryOmarchyStorage.defaultRoot()`. The space, the size and whether a virtual machine exists all come from that folder.
- `TrialRunConfiguration` names that folder as `storageRoot` in every start, so the run mode boots it and ignores the folder chosen in Try Omarchy. A Mac without an Application Support folder fails the start with `storage-unavailable`.
- `TrialVMFolder` deletes only the default folder. It opens each folder down to `shell` without following links, takes the launcher's lock on `shell/lock`, creating it if needed, and checks the path again before the move. A running virtual machine is never moved, and the folder goes to the Trash, never deleted outright.
- `Packaging/try-omarchy-kit.json` pins the kit, `TryOmarchyKit.zip` from a Try Omarchy release, by URL, size and digest, with the release's revision and the version and run-mode protocol its `TryOmarchyKit.json` declares. It also pins the `TryOmarchyKitClient` sources vendored in `Vendor/`, from the same revision.
- `scripts/try_omarchy_kit.py vendor --source ../try-omarchy --release vX.Y.Z` updates both. It refuses a release whose `TryOmarchyKit.json` names another version or another protocol than the client's. Without `--release` it vendors the client only and leaves no kit pinned.
- `scripts/try_omarchy_kit.py check` verifies the vendored client against the pin, and that a pinned kit comes from the client's revision, is a release and never `development`, and speaks the client's `VMRunProtocol.version`. `check --online` also checks the release's tag and its `TryOmarchyKit.json` against the pin.
- The kit is a helper bundle, `TryOmarchyKit.bundle`, with no bundle identifier or name of its own ([no identity](https://github.com/omacom/try-omarchy/blob/main/docs/vm-kit.md#no-identity)). Its helper and everything it starts run as this app, so the Dock, the Omarchy window and System Settings name only Omarchy Installer, and permissions are asked for and recorded in this app's name.
- `TryOmarchyKit.zip` holds that one folder. Inside it the helper is `Contents/MacOS/omarchy-vm-helper` and the manifest `Contents/Resources/kit.json`. The app keeps its kit at `Contents/Helpers/TryOmarchyKit.bundle`, and a kit it fetches as `TryOmarchyKit.bundle` in a folder of its own. These paths are spelled in one place on each side: `TryOmarchyKit.embedded()`, `TryOmarchyKit.unpacked(in:)`, `helperURL()` and `manifestURL` in the vendored client, and `kit_bundle()`, `KIT_HELPER`, `KIT_MANIFEST` and `EMBEDDED_KIT` in `scripts/try_omarchy_kit.py`.
- `scripts/try_omarchy_kit.py unpack ARCHIVE DIR` extracts a kit archive into `DIR/TryOmarchyKit.bundle`. It refuses an archive that holds anything else, a kit without its helper or manifest, and a kit with a bundle identifier or name.
- `scripts/try_omarchy_kit.py embed ARCHIVE APP` unpacks the kit into the app's `Contents/Helpers` and copies the kit's bridged-networking job, `Contents/Resources/network/launchd.plist`, to the app's `Contents/Library/LaunchDaemons/dev.tryomarchy.kit.network.plist`, with `BundleProgram` set to `Contents/Helpers/TryOmarchyKit.bundle/Contents/MacOS/omarchy-network-daemon`. It refuses a job that names another service or program ([bridged networking](https://github.com/omacom/try-omarchy/blob/main/docs/vm-kit.md#bridged-networking)).
- `scripts/try_omarchy_kit.py embed`, `release-guard` and `check-try-kit` accept only `Label`, `MachServices`, `BundleProgram`, `ProcessType`, `ExitTimeOut` and `RunAtLoad` in that job. Any other key, such as `Program`, `ProgramArguments` or `UserName`, would change what launchd runs as root, so they refuse it.
- `LiveTrialEnvironment` registers that job with `SMAppService.daemon(plistName:)`, only when the person asks. Repair unregisters and registers it again, Remove unregisters it. Both ask first, naming the shutdown when Omarchy runs, with Cancel as the default button. Both shut Omarchy down first, and neither can be chosen again until the change is done. While a fetched kit runs, the page says that its bridged networking is not available yet and offers no Set Up or Repair, and Repair is not in the menu.
- `Packaging/build-app.sh` fetches the pinned kit, checks its digest, embeds it with `embed` and runs its launcher's inspect-only check. With no kit pinned the app has no Try mode, and its pages are the installer's alone. `OMARCHY_TRY_KIT_ZIP` embeds a locally built kit instead, checked against the `.sha256` beside it.
- `Packaging/sign-vm-kit` signs every Mach-O in the kit as the installer: QEMU with the hypervisor and microphone entitlements, the helper with the camera and microphone, the bridged-networking daemon with none, then the kit's bundle. It leaves the networking client, server and supervisor as the kit signed them, because the daemon pins their bytes, and checks that `omarchy-network-daemon check` still prints `dev.tryomarchy.kit.network`. Signed ad hoc, as CI and local builds are, the kit has no hardened runtime: the hardened runtime refuses libraries that have no team, and ad hoc signatures have none, so QEMU would not load its own. A real identity keeps it. The app itself is signed with the camera and microphone entitlements, and its `Info.plist` describes their use. `Packaging/release/sign-app` does the same for releases, and `release-guard` accepts the kit in `Contents/Helpers`, refuses one with a bundle identity, and accepts only the helper's job and the kit's networking job, naming the kit's daemon, in `Contents/Library/LaunchDaemons`.
- `Packaging/release/check-try-kit` checks a signed app: the kit's bundle with no identity of its own and signed as the installer, each Mach-O in it signed as the installer, with the hardened runtime when a team signs it, except the three networking payloads, which must keep the kit's signatures, the daemon's `check`, QEMU starting from the signed app with `--version`, the app's networking job, QEMU's and the helper's entitlements, the app's usage descriptions and entitlements, and the kit's `kit.json`. With no kit pinned it checks that the app carries none.

## Newer kits

The app embeds one kit and fetches newer ones from Try Omarchy's releases, so a fix to the VM reaches people without an installer release. The embedded kit is never changed, and Try never runs a kit older than it.

- **When:** each start of Try asks, at most once a day, for `TryOmarchyKit.json` of Try Omarchy's latest published release, never a draft or a prerelease. Only Wi-Fi or Ethernet counts: on cellular or in Low Data Mode the check waits for a later start. The check runs after Omarchy starts and never delays or stops it. A fetched kit is used from the next start.
- **Which:** the release's kit must be a release, never `development`, and newer than the embedded kit and than any kit fetched before. An embedded kit without a manifest is older than any release, and an embedded `development` kit is never replaced, so nothing is asked. A kit whose run-mode protocol the vendored client does not speak needs a newer installer: it is skipped, and the current kit stays.
- **Digest:** `TryOmarchyKit.zip.sha256` names the archive's digest, and the archive must match it.
- **Unpacking:** `TrialKitArchive` unpacks the archive itself, never with `ditto`, which follows the local headers rather than the central directory.
  - The central directory may list only files and folders, all under `TryOmarchyKit.bundle`, with relative names. Names may not hold `..`, `.` or empty parts, and may not repeat, compared as APFS compares them. Entries may not carry special modes or encryption, and zip64 is refused.
  - Each entry's local header must agree with the directory on its name, method, sizes and checksum. Each entry must start where the one before it ends, and the last must end where the directory starts, so the archive holds nothing the directory leaves out.
  - Each entry is written while it inflates, and is refused once it writes more than it declares. It must then match its declared size and CRC-32. The whole kit may unpack to 4 GiB at most.
  - Files are written 0600, or 0700 when executable, and folders 0700, with no extended attributes or quarantine. AppleDouble `._` entries are skipped.
  - The unpacked folder must then hold only files with a single link and folders.
- **Contents:** the unpacked `kit.json` must equal the release's `TryOmarchyKit.json`, and its launcher must be in place.
- **Signatures:** every Mach-O in the kit must be signed with Developer ID by Try Omarchy's team (`RZC79MPD34`), with identifier `dev.tryomarchy.kit` and the hardened runtime. The Security framework checks each signature strictly, with revocation checks, and a bundle's executable stands for the bundle, its sealed resources and its nested code. The kit is a bundle, so that seal covers its scripts, firmware and guest files too. The installer's own team is not accepted: a kit it signs keeps the networking files Try Omarchy signed, so it is never one team's, and fetched kits come only from Try Omarchy's releases.
- **Every start** checks the fetched kit's signatures again, without forcing revocation checks so that Try starts offline, because its folder is writable by this user. A kit that fails, or that is no newer than the embedded one, is passed over for the embedded kit, and the reason goes to the log. It is also removed, unless another start runs it, so the next check downloads it again. The running helper's own signature is not checked after it starts, because the vendored client does not expose its process.
- **Storage:** fetched kits live in `Application Support/org.omarchy.installer/Try kits` (the workspace of the build).
  - Each kit has its own `kit-<version>-<id>` folder. The `current` link names the newest, switched in one rename, and never to a kit older than the one it names.
  - Each check downloads into an `incoming-<id>` folder of its own, and `last-check.json` records when the releases were last asked.
  - A start holds a shared lock on the kit it runs until the helper exits. A check holds an exclusive lock on its download.
  - Removing a kit or a download needs its lock, so two installers sharing the folder never remove each other's. Each start and each switch removes every other fetched kit and download whose lock is free, under the folder's own lock.
- **Failures:** a download or a check that fails removes its download and leaves the current kit in use.
- **Newer kits' events:** the client skips events and notice codes it does not know, so a newer kit's run mode never stops this installer's Try. Of the notices, Try acts on `bridged-network-unavailable` ([what people see](#what-people-see)).
- **Known limit:** bridged networking does not work from a fetched kit yet. The registered networking daemon serves only the kit beside it and pins its files, so a fetched kit starts with shared networking and the `bridged-network-unavailable` notice.
- **Code:** `TrialKitUpdater` decides and switches, `TrialKitReleases` downloads, `TrialKitArchive` reads and unpacks the archive, `TrialKitSignatureCheck` checks the signatures and `TrialKitStore` keeps the folder. `TrialKitLayout` is the one place that knows where a kit's launcher and manifest sit inside the folder a kit unpacks into.
- **Debug builds** take `OMARCHY_TRY_KIT_RELEASES_URL`, an HTTPS address or a server on this Mac, and `OMARCHY_TRY_KIT_ACCEPT_AD_HOC=1`, which accepts any valid signature, ad hoc included, for checking a locally built kit. Release builds do not contain the code that reads them.

## Testing

`TrialSessionTests` cover the landing page in every state of the inspection, Install's reasons, Try and Back, Migrate to Native and its sheet in each case, shutting Omarchy down to publish an export, the menu item's title, the two free-space numbers, the shared-networking notice and setting up, repairing and removing bridged networking, the window and the Dock tile leaving while Omarchy runs, without quitting or shutting Omarchy down, and coming back when it shuts down, fails or is reopened, a grant in System Settings showing on the next refresh, Check again, the remembered choice opening on the Try page without starting, a start that fails before the inspection, a virtual machine from Try Omarchy opening on the Try page, Try Again, Install on this Mac, a pending Recovery step found while Omarchy runs, the running page's permissions, deleting the virtual machine, and the words for every error and progress step. In debug builds they also check the pages the simulated Macs land on. `TrialVMFolderTests` cover which folders deleting may touch, links on the way, a missing lock and a lock held by another process, the default folder and the volume its space is read on, the start naming the default folder, and the start record. `TrialMigrationTests` cover the sheet's cases and which folders in the outbox count as a finished export, and `TryExportSessionTests` cover choosing the newest export and when the plan names it.

`TrialKitUpdateTests` cover fetching kits against fixtures:

- the daily check, and newer, older, equal and `development` releases;
- a kit for a newer protocol, and cellular and Low Data Mode;
- digest and checksum-file failures;
- archives whose local headers disagree with the directory, with entries the directory leaves out, a deflate bomb, wrong checksums, unsafe names, links, special modes, anything beside the kit's folder, and dropped attributes;
- the signature rules with a stand-in evaluator, and ad hoc code through the Security framework;
- a kit tampered with after its download, or failing its signature check at a start;
- a failed download that keeps the current kit, and the switch of `current`;
- two installers sharing the folder;
- a kit fetched over HTTP from a server on the loopback interface, a refused redirect, and a download past its limit.

The session tests also cover a fetched kit's shared networking, which offers no repair, and Repair and Remove refusing a second change while one runs. The views, the menu and the alerts have no automated tests, and the simulation dashboard covers the installer only.

CI runs these tests in debug and release, and `test/macos-try-tests.sh` fails when one of the three suites runs no tests or a test is skipped. `test/all` runs the pin check and the tests for `try_omarchy_kit.py` and `check-try-kit`; the macOS job runs the `unpack` tests, which need `ditto`. With a kit pinned, CI also assembles the app with it, signs it ad hoc and runs `check-try-kit` ([validation](validation.md#continuous-integration)). The pin names the kit of try-omarchy v1.3.0, a prerelease until the installer ships Try. The kit's own checks run only against a kit, locally through `OMARCHY_TRY_KIT_ZIP`: `check-try-kit`'s QEMU `--version`, `omarchy-network-daemon check` and job check, and `sign-vm-kit`'s networking steps. In `test/all` their unit tests stand in for QEMU and the daemon.

By hand on a Mac: the landing page on a supported Mac, an unsupported one and one with Omarchy installed; a second launch with a virtual machine; the first launch with a virtual machine from Try Omarchy 1.2, in the default folder and moved to another disk, which the installer leaves to Try Omarchy; Migrate to Native from the landing page, the running page and the menu, before an export, with one waiting in Omarchy and with one in Exports; Delete Virtual Machine; the error while Try Omarchy runs the virtual machine; and a fetched kit taking over at the next start, from a debug build pointed at a server on the Mac; Allow for Accessibility listing the app in System Settings; and the window closing once Omarchy is up and coming back after Shut Down. CI can't boot the virtual machine.

Start the app from the Finder or with `open`. Started from a terminal, macOS attributes its permission requests to the terminal, which System Settings lists instead. An ad hoc test build is signed with its own code hash, so macOS lists it under its path and records its grants against that build only. Each rebuild must be allowed again. Allow for Accessibility removes the row an earlier build left.
