# Repair manifest release evidence search

Observed on 2026-09-30 IST (2026-09-29 19:07 UTC). This note records a bounded, read-only first-party artifact search for the PR #29 repair compatibility review. It does not establish that a released repair manifest does not exist.

## Result

The public MX Mac Stable and RC catalogs were obtained and their Ed25519 signatures verified against the repository's existing trust root. Their authenticated installer metadata was also obtained. None of these inspected catalogs or metadata files contains a repair manifest or a reference to one. This is useful release evidence, but it does not close Marcelo's request for a producer or released repair manifest. The installer metadata's partition size is not the repair manifest's `existing_content[role].size_bytes` contract.

## Authenticated release metadata

[Stable](https://downloads.aicodelabs.com.au/channels/stable/catalog.signed.json) and [RC](https://downloads.aicodelabs.com.au/channels/rc/catalog.signed.json) both returned HTTP 200 and identical 45,336-byte envelopes. The envelope SHA-256 is `16e8b90caaf20d7c61a3b37db2909d5efe29eb9087457d48330898929d369abb`; the exact decoded catalog SHA-256 is `b595332e1b94a8ab39421e6d8808d3d67953df6fb5527f8608ac6a6a03c95507`. The catalog reports schema 4, sequence `1790210231`, issued `2026-09-24T00:37:11Z`, and evidence revision `4.0.4-mac.1.20260924-rc`.

Verification used `scripts/catalog-signing.swift verify` on the exact decoded catalog bytes and detached decoded signature, with the tracked `Release/trust-root.ed25519.pub` (SHA-256 `0e86a878c2445009981a182a4642ec22ae14ab4d8365fad4b038cafc4802dc1b`). The verifier printed `catalog_signature=passed`. The catalog was not rewritten or re-signed. Signature success authenticates these observed bytes; it is not a freshness or installation qualification claim.

The catalog lists engine, installer metadata, and payload artifacts. Its complete decoded JSON contains no repair field or repair artifact reference. The [authenticated installer metadata](https://downloads.aicodelabs.com.au/releases/os-v4.0.4-mac.1.20260924-rc/installer_data.json) is 1,004 bytes and matches the signed catalog's SHA-256 `abce392d6956e87d2fc0701d4ca42b966789494bc0647cc7062ece48a2190f6d`. It specifies EFI partition size `524288000B`, Boot partition size `2147483648B` with image `boot.img`, and Root partition minimum `34359738368B` with image `root.img` and `expand: true`. All listed partition sizes are 4096-aligned. This file is fresh-install metadata, not a repair manifest, and supplies no `existing_content[role].size_bytes` or `replacement_content[role].size_bytes` fields.

[RC Aurora](https://downloads.aicodelabs.com.au/channels/rc-aurora/catalog.signed.json) returned HTTP 200, sequence `1790127482`, issued `2026-09-23T01:38:02Z`. Its 4,596-byte envelope SHA-256 is `60d23a73ee94b70d0b880a9c4e2b1d9563cbb1e73270ffbbb15cc9f3f6810cbc`; decoded catalog SHA-256 is `4775d914df51ad1bda92e0dcceb1302d445d6603a7e1a20655b0e51281777062`. The signed Stable catalog points to [this OS ZIP](https://downloads.aicodelabs.com.au/releases/os-v4.0.4-mac.1.20260924-rc/omarchy-2026.09.23-aarch64-apple-silicon-mac-rc-os-package.zip), with size `3875382788` and SHA-256 `0920b622f67295c6a3fa7a73ba942fa6b170b4f9504a173054c2f69683909aa4`. Only its last 65,557 bytes were fetched. The server returned HTTP 206 with `Content-Range: bytes 3875317231-3875382787/3875382788`. Those range bytes have SHA-256 `a69d126683fb996008e40a035e8687f529593c36a0a079e17485d16891ba5fd6`.

The end-of-central-directory record specifies 14 entries and a 1,201-byte central directory at offset `3875381565`; the retrieved range includes that complete directory. It lists ESP files, `boot.img`, `root.img`, and `omarchy-volume.icns`, with no repair manifest member. The directory reports uncompressed `boot.img` size `2147483648` and ZIP64 `root.img` size `14344519680`, both 4096-aligned. The Root image size is different from the minimum Root partition size in installer metadata; these values must not be conflated.

These observations do not authenticate the ZIP's full digest, because the whole ZIP was deliberately not downloaded. They also cannot exclude files inside the image filesystems or prove a production repair manifest's field contract.

## Producer source trace

The installer is a consumer of an externally supplied repair manifest. At the reviewed public PR head, [`PreparationSpecification.repairManifestSourcePath`](https://github.com/omacom/omarchy-mac-installer/blob/51ad0d83513d39a499c9c167c856189248584f50/Sources/OmarchyCanaryCandidateTool/main.swift#L29-L34) supplies a file that the [candidate tool passes to the bundle writer](https://github.com/omacom/omarchy-mac-installer/blob/51ad0d83513d39a499c9c167c856189248584f50/Sources/OmarchyCanaryCandidateTool/main.swift#L214-L220). The [release staging script](https://github.com/omacom/omarchy-mac-installer/blob/51ad0d83513d39a499c9c167c856189248584f50/scripts/publish-m1-release#L181-L192) likewise copies its optional `--repair-manifest` input. Neither location computes the manifest's existing or replacement content sizes.

The original publisher's recursive source trees were inspected at the [extraction revision `4db862d`](https://github.com/maralcbr/omarchy-mx-mac/tree/4db862da7a0957758c504c5a3e041202019dbabf), [portable proof revision `8add634`](https://github.com/maralcbr/omarchy-mx-mac/tree/8add634536b87ff9121327b4972af787ea5b3cfc), and [M4 handoff revision `cf0606c`](https://github.com/maralcbr/omarchy-mx-mac/tree/cf0606c65cce20f123eb37cf465eacdb6168862b). Their repair/canary file paths identify the same consumer tools, tests, and historical non-release canary archive already characterized in [battle-testing.md](battle-testing.md#repair-manifest-compatibility-and-producer-contract). Path inspection is not a complete content search of those repositories. Searches of GitHub's default-branch code index did not locate a repair-manifest producer; historical branches and unindexed/private source are not excluded by that result.

The public image builder is available at [`maralcbr/omarchy-pkgs`, revision `7e2f6cf`](https://github.com/maralcbr/omarchy-pkgs/blob/7e2f6cfec1b3e412ad4fd6ed9611be275a246b30/bin/build-mac-image). Its `seal_images` function rounds Root image bytes up to a multiple of 1,048,576, rejects sizes exceeding the 34,359,738,368-byte Root partition minimum, and creates the Boot image at 2,147,483,648 bytes (lines 1000–1026). Both image lengths are therefore 4096-aligned. Its `write_installer_data` function emits fresh-install partition metadata (lines 1055–1066). This is direct image-producer evidence, but no repair manifest is generated in the inspected script. It does not establish how another tool chooses `existing_content[role].size_bytes`, nor that every released image came from this revision. The historical Apple image-builder tree at [`omarchy-iso` revision `7d27f99`](https://github.com/maralcbr/omarchy-iso/tree/7d27f996988eb640a0a74f67d76a1400a0cf3a80) also has image and installer-metadata producer paths but no repair-manifest-named file.

## Remaining evidence needed

Marcelo's compatibility request remains open. Closing it requires either an exact released repair manifest with provenance to the release that distributed it, or the actual repair-manifest producer at an identifiable revision with representative inputs and generated output. The output must let a test check both `existing_content[role].size_bytes` and `replacement_content[role].size_bytes` for rewritten roles against their partition capacity and 4096 alignment, plus replacement image length. A fresh-install catalog, image-builder arithmetic, or a newly invented manifest cannot establish that contract for existing repair output.

The existing checksum-pinned physical canary fixture remains the only real repair manifest obtained in this investigation. Its explicitly non-release provenance prevents treating it as a released compatibility sample. No change to the consumer's safety checks or additional synthetic fixture is justified by the evidence found here.
