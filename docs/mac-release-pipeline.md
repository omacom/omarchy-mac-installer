# Mac release pipeline

`.github/workflows/mac-release-pipeline.yml` runs one edge image from build to a signed edge catalog. It is the one Aurora image every supported Mac installs, M1, M2, M3 and the MacBook Neo alike ([hardware scope](../image-builder/README.md#hardware-scope)), and the catalog pins it for all 35 boards. `edge-dispatch.yml` starts it (`dry-run=false`, on `main`) when an edge publish changes a package the image installs. You can also start it by hand, and a manual run is a dry run unless you say otherwise. The only manual step is the owner's approval of the catalog signature.

| Job | Workflow | Runs when | Gates it keeps |
| --- | --- | --- | --- |
| `plan` | here | always | every run starts only from `main`, dry runs included (the image builds only from `main`), never for a pull request |
| `build` | `mac-image.yml` | after `plan` | no secrets; the native Recovery app built on macOS (`recovery-app.yml`) and required in the image; the release guard; a build attestation on the zip |
| `acceptance` | `mac-acceptance.yml` | after `build` | main only, never for a pull request; the zip's sha256 and build attestation checked; the VM harness's `fresh-install` scenarios on the VM runner ([runner](mac-acceptance-runner.md)); fails unless the evidence record for the zip's sha256 passes; a passing record is attested |
| `catalog-inputs` | here | acceptance passed | `.github/mac-release-pipeline.json` must name a published app release (a dry run only notes it), before anything is public |
| `upload` | `mac-upload.yml` | acceptance `result == pass`, catalog inputs read | `publish` environment (main only); evidence and attestation re-checked; never overwrites; on a real run, `host: github-release` publishes the draft as a prerelease (never latest), and `host: r2` is public as written at `mac.omarchy.org/v1/releases/<image>/` ([hosts](mac-upload.md#hosts)) |
| `catalog` | `mac-catalog.yml` | real run, all of the above succeeded | evidence re-checked for the payload's digest; every URL serves its pinned bytes; `catalog-release` (owner approval, main only) signs |

A dry run uploads to a `dryrun-` scratch release and deletes it, and signs no catalog. A catalog dry run needs files the app can download, so run `mac-catalog.yml` by hand for that.

## What passes between jobs

- `build` outputs `name` (also the image artifact's name), `payload` (the zip's file name) and `sha256`. Inside it, the macOS `recovery` job (`recovery-app.yml`) builds the native Recovery app and keeps it as the GitHub artifact `native-recovery-input` with its inventory digest as an output; the image job checks the downloaded app against that digest and builds with `--recovery-app`, so every image the pipeline (and `edge-dispatch.yml`) builds declares `recovery_gui: omarchy-native-v1` and carries `esp/aurora/recovery/Omarchy Installer.app`.
- The image never leaves Namespace: `build` (on Namespace's Apple-backed Linux ARM64 runner), `acceptance` and `upload` (on Namespace runners) pass it through Namespace's artifact storage (`namespace-actions/upload-artifact` and `download-artifact`), about 10 s for the 3.4 GB zip each way. No pull request reaches a Namespace runner: acceptance's VM job waits for its GitHub-hosted `guard`, and the build and upload jobs carry the same refusal in their own `if:` (the build also requires `main`). The small artifacts (evidence, logs) stay GitHub artifacts.
- `acceptance` uploads the artifact `acceptance-evidence`, holding `acceptance-evidence.json` ([format](mac-acceptance-evidence.md)), and outputs `result`, `evidence-artifact` and `evidence-run-id` (this run). It also keeps the harness's logs as `acceptance-harness-logs`. The pipeline's `runner` input (empty by default) overrides the VM job's runner.
- `upload` downloads the image and evidence artifacts from this run. After a real upload it outputs `payload` and `installer-data` (the catalog's inputs, built from the files it uploaded and verified) and `evidence` (the record it checked).
- `catalog-inputs` outputs the catalog's `engine` block (the engine `Engine/source-lock.json` pins, with the config's `downstreamRevision`) and the `installer` block of `.github/mac-release-pipeline.json`.

## Where the jobs run

Namespace builds and publishes the image. Namespace is a Distinguished Corporate Patron of the Omacom Foundation, giving $100,000 a year in compute for three years for ARM builds and QA ([announcement](https://omarchy.org/news/2026/10/namespace-joins-as-a-distinguished-corporate-patron/)), so its runners are our CI, like GitHub's. `build` runs on Namespace's Apple-backed Linux ARM64 runner. `upload` runs on a Namespace runner too, with `contents: write` and, with `host: r2`, the R2 credentials in the `publish` environment. It is the first job with write access that runs off GitHub's hosted runners. The guards and the jobs that hold `id-token`, `attest` in `mac-image.yml` and in `mac-acceptance.yml`, stay on GitHub-hosted runners.

So when acceptance and upload run `gh attestation verify --deny-self-hosted-runners`, they check that the attestation was signed by `mac-image.yml` on `main` in its GitHub-hosted `attest` job, over the digest `build` reported. They do not check that the zip was built on a GitHub-hosted runner: Namespace built it.

## Secrets

The only secret is `CATALOG_SIGNING_KEY`, an environment secret of `catalog-release`. The pipeline passes it to `mac-catalog.yml` by name and never uses `secrets: inherit`. GitHub delivers an environment secret to a called workflow only when the caller passes it, and only to the job that runs in that environment. A throwaway probe (run 38553165283) confirmed this: passed by name or with inherit, the secret reached the job in the environment but not a job without it, and not passed, it reached neither. A second probe (run 38558712893) checked one more level of nesting, which is what happens once #69 moves signing into `mac-catalog-sign.yml`: when the pipeline passes the key by name and `mac-catalog.yml` forwards it, by name or with `inherit`, the key reaches the sign job. When the pipeline passes nothing, it stays empty. `mac-catalog.yml` can only forward what it was given, which here is the key alone. The pipeline's `upload` job passes the `publish` environment's R2 credentials (`R2_ENDPOINT`, `R2_ACCESS_KEY_ID`, `R2_SECRET_ACCESS_KEY`) to `mac-upload.yml` by name in the same way. The pipeline's `host` input (default `r2`; `github-release` is the fallback) picks where the image goes ([hosts](mac-upload.md#hosts)).

The catalog takes the evidence record the upload checked, and the upload took it from this run's acceptance artifact, with the attestation `mac-acceptance.yml`'s `attest` job made for it. The acceptance workflow uses no secrets.

## `.github/mac-release-pipeline.json`

- `engine`: only `{"downstreamRevision"}`. The run's engine is the one `Engine/source-lock.json` pins, the only place the engine is pinned ([Engine versions](engine-versions.md)); `catalog-inputs` adds its version, file name, size and digest, and its URL under the catalog base's `engine/<version>/` (`catalog_release.pipeline_engine`), where `mac-mirror.yml` copies it from its published `engine-<version>` release.
- `installer`: the app compatibility block, `{"minimumVersion", "latestVersion", "downloadURL"}`: app 2.3.0, the floor `Engine/source-lock.json` sets for its engine (`downstream_overlay.minimum_app_version`), and its published `.dmg`, from the catalog base's `installer/<version>/`, where `mac-mirror.yml` (`artifact: app`) copies it from the published `v<version>` release. A `null` block (no app release at all) makes `catalog-inputs` refuse on a real run with a message saying so, before the upload, so nothing is made public. `minimumVersion` 2.3.0 makes every edge user, M1, M2 and M3 included, update the app before their next install.

### Pin pull requests

Publishing an app release (`v<X.Y.Z>`) or an engine release (`engine-<version>`) starts `mac-pipeline-pins.yml`, which runs `scripts/pipeline_pins.py` on main and opens a pull request moving this file to it, with the release asset's sha256 in the body. An app release moves `installer.latestVersion` and `installer.downloadURL` to its dmg under the catalog base, unless the config already pins that app or a later one. An engine release moves `engine.downstreamRevision`, here and in the release-inputs templates, to the release's commit, and is refused unless it is the engine `Engine/source-lock.json` pins and its archive is the lock's. `installer.minimumVersion` never moves in these pull requests: it is the floor of apps a catalog accepts and changes only in a pull request of its own; a bump the catalog's checks refuse under it fails the run and opens nothing. An app bump is also refused while a published `catalog-rc` or `catalog-stable` pins an engine digest other than the one `Engine/source-lock.json` pins or the lane's recorded hold ([Lane holds](catalog-release.md#lane-holds)): `installer.latestVersion` must not outrun the engine an install downloads. Publish the channel catalog first; an engine bump answers to no catalog, since installs always follow the pins forward. A refused app bump opens no pull request: re-sign the lane on the locked engine (`mac-catalog.yml`), then dispatch `mac-pipeline-pins.yml` with the app's `tag`. `checks.yml` repeats the check on the pin pull request's own branch when a branch moves `installer.latestVersion` against its merge base with main, against the catalogs live at that run and the branch's `Engine/source-lock.json`, because the catalogs can move between the bump and the merge. An engine whose `minimum_app_version` is the app released with it has no pin route: the engine pin fails `check_installer` under the old floor, and the app pin waits on catalogs that pin the new engine. Sign rc and stable by hand with `mac-catalog.yml`, passing its `engine` and an `installer` input at that app, then dispatch the app's pin, then raise `installer.minimumVersion` in a pull request of its own. This keeps the pipeline config from offering an app while a lane is off-lock; it cannot stop the dmg from shipping first, or a catalog from changing after CI. Merge a pin pull request after `mac-mirror.yml` has copied the release to R2. A pull request opened with the workflow token starts no `pull_request` runs, so the workflow dispatches `Installer checks` on its branch. A dispatch with a `tag` pins a release published earlier, or retries a failed run.

## New installs only

The image is what a new install writes, and the builder migrates nothing installed. The boot loader packages do, under their own review and approval: `m1n1-aurora` (omacom/omarchy-pkgs#1513) upgrades in place where it is installed and replaces `m1n1-neo` by name, and on edge `aura` replaces `m1n1-aurora` (omacom/omarchy-pkgs#3025, with the 7.3 kernel). An installed Mac therefore gets a new ESP Stage 2 at its next update, never a new enrolled Stage 1, and keeps its U-Boot provider. Edge images install `aura` and enroll `m1n1-aurora`'s raw Stage 1 on a new MacBook Neo (`channel.lanes.edge.boot_loader` in the trust policy). Everything else stays: an existing M1, M2 or M3 install keeps `uboot-asahi`, stock `mesa` and `asahi-audio`. The other Aurora packages carry no `replaces=` on those names, and nothing here moves them; later package or hook changes could, and would need their own review. The builder's substitution and the policy's refusal of the old boot chain apply to the image alone; they are not an upgrade path. Moving installed Macs to the Aurora stack would be a separate change, with its own owner.

## Promotion

A release tag builds a release image instead of an edge one: `release-tag=v4.5.0-rc2` builds from the rc channel and publishes `catalog-rc`, and `release-tag=v4.5.0` builds from the stable channel and publishes `catalog-stable`. Stable can only be built once rc has been promoted to stable, because the builder requires the tag's `omarchy` in that channel. To install the final packages before that promotion, `release-tag=v4.5.0` with `final-tag-on-rc=true` builds from the rc channel and publishes `catalog-rc`. That image is named `omarchy-mac-4.5.0-rc-r<revision>-...`, its bare `-rc` keeps it apart from the stable image, and `catalog-stable` refuses it, by build or by promotion. Both are started by hand and keep the same gates as an edge run.

Catalog promotion to rc and stable is parked. When unparked, it carries the edge catalog unchanged: the Aurora image, the edge runtime, the MacBook Neo, and whatever preview notes and installer minimum the edge catalog carries ([what a promotion carries](catalog-release.md#promotion-parked)). Accepting that is a maintainer decision to record first.

## Qualification on edge

Edge is for the testing team, so newly supported Macs are qualified there, on real hardware, after an edge release: until then they are qualified only for `edge` in `scripts/supported-models.json`, which keeps them out of rc and stable and gives edge's catalog the note the app shows. The 11 supported M3 boards and the MacBook Neo have since been installed and run on real hardware and are no longer marked. Nothing waits for a hardware install before an image reaches edge; the automated gates above (the release guard, inspection, VM acceptance and both attestations) still stop every image that fails them. The VM harness boots the image's userland under an M1 Pro identity with a generic kernel; m1n1, Stage 1, the Aurora kernel and every board's hardware are qualified on a real Mac.
